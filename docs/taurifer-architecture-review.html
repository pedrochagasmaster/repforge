Codebase design review / Taurifer

Deepen ownership, not the directory tree.

Taurifer already has a strong domain core. The next architectural move is to make the remaining cross-cutting workflows belong to one module each—especially durable local state, workout session, entry, and gestures.

Recommendation

Keep Taurifer statically deployed with a small number of deep JavaScript modules.
Do not rewrite it in a framework, replace the storage protocol, or turn every screen into an independently managed subsystem.

The main issue is not that app.js is large. It is that callers still understand details that should belong to the implementation: draft receipts, replica outcomes, recovery timing, setup-draft cleanup, and another module's event-listener identities.

Priority findings

Highest leverage
Durable commit + recovery

One module should own journals, locks, replica settlement, recovery, and stable outcomes. Structural transitions require both replicas for committed; preserve partial-write truth, existing bytes, and compatibility while extracting.

Strong
Workout-session lifecycle

Keep DraftV2. Move pending-work acknowledgement, finish ordering, recovery actions, and completion outcomes behind a session interface.

Safest first refactor
Gesture ownership

Replace boot polling and cross-file listener takeover with one explicit mount/dispose owner that chooses Motion or fallback behavior.

Strong
Entry + activation workflow

Keep the existing pure entry state machine and compiler adapter; deepen the imperative host around setup-draft lifetime, reviewed candidate, activation, and cleanup.

Worth proving
Historical projections

Extract only a proven shared projection with at least two genuine consumers. Do not create a generic read-model subsystem by default.

Cross-cutting
Release + test ownership

Source guards must follow extracted runtime files. Behavioral tests should exercise production interfaces, while CI keeps one executable inventory.

Target direction

Before
UI / host code knows workflow protocol

Renderers and entry/workout callers assemble persistence details, interpret low-level outcomes, or coordinate another module's lifetime.

→
After
Workflow owners expose stable outcomes

Renderers consume acknowledged projections and outcomes. Durable state has one owner. Pure domain modules remain independent of DOM, telemetry, and app host.

A refactor is successful when it removes knowledge from callers—not merely lines from app.js.

Guardrails

No framework rewrite

No React, global state library, DI framework, bundler, or TypeScript migration as a prerequisite.

No storage redesign

Retain historical keys, IndexedDB names, lock identifiers, WAL/checkpoint/tombstone semantics, and supported legacy readers during extraction.

No fake generality

No generic event bus, repository abstraction, global utility bag, or one-file-per-helper decomposition.

No product-scope expansion

Do not turn install transfer into account sync, couple training to telemetry, or create entitlement architecture as part of the refactor.
