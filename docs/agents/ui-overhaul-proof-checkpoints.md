# First proof checkpoints for the UI overhaul

These checkpoints operationalize existing Plans 049–059. They do not replace
their acceptance criteria or change the delivery DAG. The approved recovery
and transfer contracts are fixed; downstream staging, physical-device, and
landing-asset gates remain where the plans name them.
Use the [evidence protocol](implementation-evidence.md) in every plan PR.
Record the actual command and assertion path when its first slice lands.

## Plan 049: canonical reconciliation

Treat transfer, transition identity, recovery policy, and semantic UI roles as
separate architecture checkpoints inside the phase. Validate a normalized clone
through `app.js` save/load and `program-compiler.js` structure migration; validate
transition examples against compiled programs and progression relations. Check
all consumers and examples from one authoritative contract. Deliberately remove
structure, duplicate a target, alter a hash preimage, and drift an enum to prove
the checks reject them. The selected provider and recovery policy are checked
as closed Phase 0 contracts; staging and physical-device evidence remain
downstream gates.
The existing PR owns these corrections; this workflow creates no competing schema.

## Plan 050: proven defects and catalog leverage

Start with one production catalog state that currently fails the approved copy
or geometry invariant. Prove the detector fails on raw rendered keys and an
overlapping control, then passes the repaired state. Include an intentional
scroller that stays allowed. Use `tools/capture-ui-screens.mjs`, the actual
scenario, and EN/PT-BR rendered evidence before applying the matrix broadly.
Catalog registration alone does not establish layout correctness.

## Plan 051: workout draft state

Trace a programmed set through edit, commit, correction, persistence, reload,
and save using `app.js` and the Focus/browser suites. Prove values survive without
hidden List inputs. Interrupt a write, use a stale second tab, and remove/resume
a draft. Compare the entire logical set identity and values after recovery.
Pure DraftV2 tests alone do not close the storage or DOM-ownership gate.

## Plan 052: block transitions

Compile one real sibling pair using `program-compiler.js` and the entry adapter.
Generate a proposal, show its exact diff, confirm it, reload, and inspect the
successor and archive. Verify total one-to-one identity coverage, matching rules,
array order, strategy/relations, hash, stale rejection, and idempotent commit.
Reject duplicate targets and unsupported reconstruction before expanding to
all families. Recovery-dependent work waits for its policy selection.

## Plan 053: installation transfer

Use isolated browser and installed storage contexts with the approved service
contract. Clone an actual normalized device state with log/history, custom
definitions, active draft, preferences, and consent; compare all logical fields
after import and reload. Test lost create response, claim/commit crashes, expiry,
credential loss, and browser divergence. Check exact service/client limits and
privacy behavior. The selected Cloudflare/EU contract precedes implementation;
drift is a STOP condition. Emulation cannot close the physical iOS handoff
gate.

## Plan 054: landing and program entry

Prove a valid received setup enters its adaptive first-run route and writes no
candidate field before explicit activation. Cover cancellation, return without
a program, and all five entry jobs through the real `program-entry.js` and
`program-entry-adapter.js` consumers. Prove the installation offer respects context
and data state. Image generation and owner selection remain prerequisites for the
landing reference, and physical review remains required by the plan.

## Plan 055: Focus-only workout

Complete one production session through Focus: inspect, edit, substitute,
warm-up, skip/restore, repeat-last, correct, leave/resume, save, and summary.
Record each retained capability's new location in the parity table. Prove Preview
does not create a draft. Delete List only after state ownership and parity pass.
Validate phone operation, focus, reduced motion, and scaling before broad polish.

## Plan 056: Progress and block lifecycle

Use real logs and a known schedule to exercise zero/one/two/three-point evidence,
elapsed-week volume, and current-block versus all-history scope. Test labels
against calculated denominators. Trace one eligible action through Plan 052's
proposal/confirmation/archive path; insufficient evidence must not produce that
proposal. Recovery must preserve policy version 2, its explicit confirmation,
allowlist, and reassessment contract.

## Plan 057: management surfaces

Start with History read, edit, cancel, save, and confirmed deletion using persisted
sessions. Verify the read path never writes. Exercise Share with multiple unresolved
identities: every blocker appears, each repair returns to Share, and nothing is
silently omitted. Then cover summary, Today, Program, Settings, and timer invariants
from the plan with compact, scaled, and localized production frames.

## Plan 058: design-system convergence

Inventory actual rendered roles across all public surfaces. Migrate one example
of each role and validate text/icon/boundary contrast in both themes and all
required states. Include disabled and decorative exceptions explicitly. Expand
only after the role works across its consumers. A token declaration, literal
count, or orange replacement is not evidence of rendered-role AA compliance.

## Plan 059: public-launch validation

Pin the release candidate and account for every manifest state and approved
matrix variant. Run complete journeys and actual scroll-end checks, then collect
physical Safari/PWA/VoiceOver and Chrome/PWA/TalkBack evidence against that
candidate. Reconcile shipped UI, docs, telemetry/privacy, tests, catalog, and
service-worker inventory. New fixes require affected evidence again. Owner
sign-off closes the gate; automated results cannot supply it.

## Adopt without disrupting active work

The workflow PR branches from main independently of PR #222. It changes no
Phase 049 schemas, checkers, fixtures, or acceptance decisions. The current
implementer can apply these proof methods to the ongoing corrections. After
both PRs merge, downstream agents fetch main and use the protocol and checkpoint
links already embedded in their plans. Preserve #222's documentation updates
when merging the independent instruction additions.
